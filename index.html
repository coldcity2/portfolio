Deep Dive 1 — AI

AI 레시피 생성을 사용자 대기형 API에서 Job/Polling 기반 비동기 파이프라인으로 재설계

1. 문제 정의

AI 레시피 생성은 완료까지 수십 초 이상 걸리는 장시간 작업이었습니다. 처음에는 하나의 HTTP 요청 안에서 이 시간을 그대로 기다리게 하는 구조였습니다. 문제는 응답 지연 자체가 아니라, 사용자가 기다리는 동안 일어나는 일이었습니다. 생성 중에 앱을 종료하거나 페이지를 새로고침하면 진행 상태를 알 수 없었고, 사용자는 생성이 됐는지 안 됐는지 모른 채 같은 요청을 다시 보냈습니다. DB를 확인해 보니 동일 조건으로 2~4회 연속 생성 요청이 들어오는 경우가 발견되었습니다. 페이지 이탈을 막으면 해결될 거라 생각했지만, 네트워크 끊김이나 앱 강제 종료까지 막을 수는 없었습니다.

결국 요청과 생성 작업을 분리하지 않으면 이 문제는 구조적으로 해결할 수 없다는 판단에 이르렀습니다.

2. 해결

그래서 요청을 받으면 즉시 jobId를 반환하고, 실제 생성은 백그라운드에서 처리한 뒤 상태를 polling 하도록 구조를 바꿨습니다. 핵심은 모델을 더 빠르게 만드는 것이 아니라, 사용자가 언제 이탈하더라도 작업 상태를 추적하고 정합성을 유지할 수 있는 구조를 만드는 것이었습니다.

이 구조를 실제 서비스에 넣으려니 세 가지를 함께 고려해야 했습니다.

1) 작업 종류가 다르면 경로도 달라야 했다

모든 AI 요청이 같은 방식으로 끝나지 않았습니다.

  • TEXT_MODE / IMAGE_MODE 분리
  • concept별 생성 경로 분리

실측 결과, 단일 텍스트 경로는 약 22초, 2단계 생성 경로는 약 75초, 이미지 포함 경로는 약 43초 수준으로 차이가 커 하나의 blocking API로 다루기 어려웠습니다.

2) 실패하거나 겹칠 때 정합성이 깨지면 안 됐다

비동기 구조에서는 요청이 실패하거나 동시에 들어올 때 상태와 크레딧이 쉽게 어긋날 수 있었습니다.

  • 같은 실패 job에 대해 환불이 중복 적용되지 않도록 환불 transaction id를 고정
  • 같은 요청이 동시에 들어와도 job이 하나만 생성되도록 멱등성 키와 DB 제약조건 적용

3) 과부하와 멈춤에 대한 안전망이 필요했다

장시간 작업은 잘 동작할 때보다, 서버가 바쁘거나 작업이 멈출 때가 더 위험했습니다.

  • 과부하로 제출이 거절되면 FAILED + refund로 정리
  • 일정 시간 이상 멈춘 job은 scheduler가 감지해 recovery 수행
  • fake provider로 실패, 재시도, 포화 시나리오를 반복 검증

3. 결과

1) 사용자 경험은 41초에서 204ms로 바뀌었다

같은 이미지 포함 요청 기준으로 V1과 V2를 비교한 결과입니다.

경로Initial Response P50Initial Response P95Job Total P50
V1 blocking 41,107 ms 50,039 ms 41,107 ms
V2 job/polling 204 ms 220 ms 43,043 ms
실제 완료 시간은 여전히 수십 초였지만, 사용자가 기다리는 시간은 41.1초 → 204ms로 바뀌었습니다.

2) 측정과 검증으로 구조적 위험을 확인했다

대표 경로를 phase별로 계측한 결과, text_generation은 5.35초, db_save는 0.25초 수준으로 병목이 DB 저장이 아니라 text generation 구간에 집중되어 있었습니다. 진행률 모델도 이 실측에 맞춰 설계했습니다.

fake provider로 실패·재시도·포화 시나리오를 반복 검증하는 과정에서, 초기 retry 경계가 비동기 경로에서 기대대로 동작하지 않는 문제를 발견했고 동기 invoker 계층으로 옮겨 수정했습니다.

운영 정합성도 함께 검증했습니다.

  • 동시 요청 시 job 1개만 생성, 중복 환불 방지
  • 과부하 시 즉시 실패 처리 + 크레딧 환불
  • 중단된 job 자동 복구

특히 포화 검증은 tiny executor(core=1, max=1, queue=0) 환경에서 5건 동시 요청 중 1건만 처리되고, 나머지 4건이 즉시 FAILED + refund로 정리되는지 확인한 테스트였습니다.

현재 구조는 단일 서버 ThreadPool 기준이라 더 큰 규모에서는 메시지 큐 기반 확장이 필요하지만, 피크 기준 하루 AI 레시피 234건 생성, YouTube 레시피 390건 추출 요청이 에러 없이 처리되었고, 호출이 몰리는 시간대에 실패한 건에 대해서는 정상적으로 크레딧이 환불됨을 확인했습니다.

이 경험을 통해 정상 경로만 구현해서 끝나는 것이 아니라, 사용자의 이탈과 네트워크 끊김, 중복 요청 같은 엣지 케이스까지 먼저 고려해야 안정적으로 운영할 수 있는 서비스를 만들 수 있다는 기준이 생겼습니다.

Deep Dive 2 — 검색

검색 엔진 장애 시에도 멈추지 않는 하이브리드 검색 구조와 fallback 설계

1. 문제 정의

레시피 검색은 사용자가 서비스를 탐색할 때 가장 자주 거치는 핵심 경로였습니다. 실제 운영 과정에서도 검색 응답이 느려지는 구간이 있었고, 레시피 수와 요청이 늘어날수록 DB 기반 검색만으로는 한계가 분명해졌습니다. 성능을 개선하기 위해 OpenSearch를 도입하려 했지만, 프리티어 환경에서는 외부 검색 엔진에 대한 의존 자체가 새로운 리스크로 느껴졌습니다. 검색이 빨라지더라도 장애가 나면 서비스 전체가 멈출 수 있기 때문입니다.

핵심은 단순히 "OpenSearch가 빠른가"가 아니라, 성능을 높이면서도 장애 시 검색이 계속 동작하는 구조를 만들 수 있는가였습니다.

2. 해결

그래서 검색은 한 가지 경로로만 설계하지 않았습니다. OpenSearch를 주 검색 경로로 두고, 장애 시에는 QueryDSL 기반 DB 검색으로 자동 fallback 되도록 이중 구조를 만들었습니다. 또한 인덱싱은 쓰기 트랜잭션과 분리해, 검색 품질 문제가 요청 실패로 바로 번지지 않도록 했습니다. 검증하는 과정에서 다음을 고려해야 했습니다.

1) 먼저, 공정하게 비교할 수 있는 환경이 필요했다

"OpenSearch가 빠를 것 같다"는 가정만으로는 설득력이 없었기 때문에, 운영과 분리된 benchmark 환경을 먼저 만들었습니다.

  • production snapshot 기반 benchmark copy RDS (사용자 정보 익명화)
  • 로컬 OpenSearch 2.17.1 단일 노드 + SSH 터널 DB 연결
  • 동시성 1 / 5 / 10, 반복 3회, 엔진당 총 요청 수 11,700건

2) 외부 검색 엔진에 의존할수록, 장애 시 대안도 함께 설계해야 했다

OpenSearch를 주 경로로 두는 순간 검색 엔진 장애가 곧 서비스 중단으로 이어질 수 있었습니다.

  • search.engine=auto 기반 이중 경로
  • OpenSearch 실패 시 QueryDSL fallback

3) 검색 인덱싱은 요청 정합성과 분리해야 했다

인덱싱 실패가 사용자 요청 실패로 바로 이어지면 안 됐기 때문에, 쓰기 요청과 검색 인덱싱의 책임을 분리했습니다.

  • AFTER_COMMIT 기반 인덱싱
  • 인덱싱 실패 시 별도 로그 기록 + 복구 배치로 누락 보완
  • 냉장고 검색: 역인덱싱·재료 동의어로 AI·YouTube 레시피 누락을 보완하고 보유 재료 매칭률로 정렬

원본 데이터의 기준은 MySQL이 유지하고, OpenSearch는 읽기 성능을 담당하도록 역할을 나눴습니다.

4) fallback도 실제 운영 경로이므로 함께 최적화했다

검색 엔진 장애 시 모든 요청이 DB로 몰릴 수 있으므로 fallback을 느린 예비 경로로 남겨두지 않았습니다. LIKE OR 풀스캔을 MySQL ngram FULLTEXT로 전환하고, 목록은 먼저 ID를 좁힌 뒤 필요한 projection만 읽도록 구성했습니다.

  • 필터 사용 여부에 따라 불필요한 JOIN과 count JOIN 제거
  • FULLTEXT 후보 범위 제한 · 정렬 조건별 복합 인덱스 · ID 우선 조회

3. 결과

1) OpenSearch는 동시 요청 구간에서 확실히 빨랐다

v2-search 기준 concurrency별 P95 비교 결과입니다.

3) 운영 관측까지 보강했다

검색 지연, fallback 전환 횟수, 엔진 상태 변화를 메트릭으로 추적했고, 요청 단위 traceId로 검색 요청부터 fallback 전환까지 같은 흐름으로 추적할 수 있도록 구성했습니다. 인덱싱 실패는 별도 로그로 기록하고 복구 서비스로 보완했으며, 새 인덱스는 bulk reindex 후 실패 ID를 확인하고 alias를 교체할 수 있도록 구성했습니다.

이 결과는 로컬 benchmark와 SSH 터널 기반 환경에서 얻은 수치이므로 절대 latency 자체를 그대로 일반화하진 않았습니다. 다만 같은 데이터와 같은 요청 세트에서 QueryDSL과 OpenSearch를 반복 비교해 상대적인 차이를 확인했고, 배포 이후 DAU 약 2,500 규모의 운영 구간에서도 검색 응답 오류 없이 동작해 구조적 판단의 방향이 틀리지 않았음을 확인했습니다.

1. 문제 정의

운영 환경은 ddl-auto: none으로 두고 Flyway가 스키마를 관리했습니다. 하지만 모든 DDL을 애플리케이션 시작 시 자동 적용하면, 레거시 컬럼 삭제나 FULLTEXT 인덱스 재구성처럼 오래 걸리는 작업 하나가 metadata lock과 애플리케이션 기동 실패로 이어질 수 있었습니다. 코드가 더 이상 컬럼을 읽지 않는 것과 운영 DB에서 지금 바로 안전하게 삭제할 수 있는 것은 다른 문제였습니다.

핵심은 migration을 많이 만드는 것이 아니라, 배포 과정에서 자동화해도 되는 변경과 운영자가 확인한 뒤 실행해야 하는 변경의 경계를 정하는 것이었습니다.

3. 실제 판단이 바뀐 사례

자동 DROP을 배포에서 분리했다

recipes.extractor_id의 source of truth를 별도 YouTube 정보 테이블로 옮긴 뒤 처음에는 자동 DROP migration을 작성했습니다. 그러나 DROP 실패가 Flyway를 통해 애플리케이션 시작까지 막을 수 있어, 코드 전환은 먼저 배포하고 물리 삭제는 검증 쿼리가 모두 0인 저트래픽 시간대에 수동 실행하도록 변경했습니다.

대량 변경은 멱등한 작은 단위로 실행했다

이미지 생성 모델 백필은 대상 건수를 먼저 확인하고 IS NULL 조건으로 1,000건씩 반복 UPDATE했습니다. 레거시 컬럼 정리는 실행 전 누락과 상태 불일치를 확인하고, 실행 후 잔존 컬럼·인덱스가 0인지 다시 검사하도록 구성했습니다.

수동 작업은 배포 자동화 수준을 낮추고 운영 절차를 요구합니다. 대신 현재 규모에서는 애플리케이션 기동과 파괴적 DDL을 분리하는 편이 안전하다고 판단했습니다. FULLTEXT가 걸린 테이블의 ALGORITHM=COPY처럼 write lock이 불가피한 변경은 작업 시간과 테이블 크기를 먼저 확인해야 합니다.

frontend revalidation이 실패해도 이미 커밋된 route 상태를 되돌리지 않습니다. 호출 실패는 로그로 관측하고, 최근 변경 route를 다시 동기화하는 scheduler와 일일 사이트맵 재생성으로 복구합니다. 동일 route의 사이트맵 삭제·재삽입과 revalidation은 반복 실행 가능한 형태로 구성했습니다.

현재 규모에 맞춘 선택과 다음 확장

동일 site·locale·날짜의 실행은 run row lock으로 직렬화되며, SKIP LOCKED는 route 수준 경합을 방어합니다. 현재 후처리는 짧은 캐시 TTL과 최근 변경 재처리로 회복 가능해 별도 Outbox를 두지 않았습니다.

릴리스 규모가 커지면 최근 route를 한 번에 읽는 복구 조회를 DB pagination으로 바꾸고, 장시간 외부 장애까지 전달 보장을 요구하면 Transactional Outbox와 비동기 consumer로 확장해야 합니다. 현재 구조에서는 quota의 DB 정합성을 우선하고 외부 후처리는 eventual consistency로 분리했습니다.

이 경험을 통해 동시성 문제를 특정 락 기술로 시작하기보다, 반드시 지켜야 할 불변식과 실패해도 되는 경계를 먼저 정의해야 운영 가능한 플랫폼을 만들 수 있다는 기준이 생겼습니다.

Deep Dive 5 — 제한된 외부 API

분당 호출 제한이 있는 Coupang Search API를 사용자 요청에서 분리한 DB 기반 수집 파이프라인

1. 문제 정의

AI 레시피가 생성될 때마다 재료별 상품을 즉시 검색하면 한 레시피에서도 여러 번 외부 API를 호출하게 됩니다. 사용자와 레시피가 늘수록 호출량이 그대로 증가해 쿠팡 Search API의 분당 호출 제한과 429에 부딪히고, 외부 장애가 레시피 생성 지연이나 실패로 번질 수 있었습니다. 동일한 ‘양파’를 여러 레시피가 사용해도 매번 다시 검색하는 구조 역시 낭비였습니다.

해결 목표는 API를 더 빨리 호출하는 것이 아니라, 사용자 요청량과 외부 API 호출량의 결합을 끊고 동일 재료의 결과를 서비스 전체에서 재사용하는 것이었습니다.

READY·NO_RESULT·ERROR 상태와 상품·다음 시도 시각을 짧은 트랜잭션으로 반영

호출 제한과 장애를 파이프라인 전체가 함께 흡수한다

  • 기본 3초 fixed delay + 단일 thread executor로 한 인스턴스에서 이론상 분당 20회 이하로 pacing
  • 일반 오류는 1시간부터 지수 백오프하고 최대 5회까지만 자동 재시도
  • 429 발생 시 현재 row의 lock을 해제하고 Redis에 전역 halt를 기록해 모든 worker가 호출을 중단
  • 기본 정책은 KST 다음 날 00:10 재개이며, 관리자 API에서 pause·resume·상태와 남은 TTL 확인
  • Redis 제어 상태를 읽지 못하면 새 API 호출을 멈추는 fail-closed 방식 적용
결과적으로 사용자 API는 쿠팡 호출 한도와 무관하게 DB에 저장된 상품을 응답하고, 외부 호출은 정규화된 재료 단위로 공유·우선순위화·지연 실행됩니다. 사용자 요청량이 늘어도 외부 호출량이 같은 비율로 증가하지 않는 구조를 만들었습니다.
현재 pacing과 AtomicBoolean은 단일 애플리케이션 인스턴스를 기준으로 합니다. 여러 ECS task가 동시에 worker를 실행하면 SKIP LOCKED는 중복 작업은 막지만 전체 호출 수의 합계를 제한하지는 않습니다. 다중 인스턴스 확장 시에는 Redis token bucket 또는 DB의 전역 next-call row로 호출 quota를 공유해야 합니다.
